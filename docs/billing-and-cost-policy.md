# 成本归属与计费口径（决策记录，2026-09-23）

> 起因（用户提出）：**用户提交的任务上游已经收到并消耗了额度，但我们没把结果交给用户 —— 这笔消耗算谁的？**
> 这份文档就是那个「说法」。结论先行，后面给证据与落地动作。

---

## 一、先澄清事实（都已实测/查证）

| 事实 | 依据 |
|---|---|
| **我们服务端没有「按用户扣积分」的实现** | 全仓库检索 `power / 扣减 / consume / deduct / balance`，只命中 `marketing-center`、`research` 两个无关模块 |
| 界面上那个「1020」是**上游账户余额**，不是我们自己的用户积分账本 | 它由目录/上游余额接口驱动；我们没有本地积分流水表 |
| **上游按调用计费，与是否交付无关** | 上游是 API 网关计费：收到请求即计费，与我们是否把结果落给用户无关 |
| 上游结果返回率约 99%（用户观察） | 与我今晚实测一致：24/24、以及多次单张生成都成功返回 |
| **任务完成后结果会留在资产里**，不依赖用户窗口是否还开着（用户已确认） | 服务端记录 + 资产条目；这也解释了「退出窗口后结果还在」体验良好 |

**所以真正的结论是**：成本发生在我们**上游账户**；用户侧目前不存在「已被扣积分」这件事（我们没实现扣减）。

---

## 二、裁定（对外口径 + 对内责任）

**1. 用户不承担任何未交付的消耗。**
未拿到结果 = 未交付。用户既不应当被扣积分，也不应当被要求「再试一次」而重复付出 ——
**重试不产生二次计费**（我们的实现本来就不按次数扣费；未来接入正式计费时，这条要写死在规则里）。

**2. 成本由平台承担。**
上游已消耗但未交付的部分，计入平台成本（计入渠道损耗），**不向用户追偿**。
理由（权益 + 我们自身利益一致）：
- 用户为「结果」付费，不是为「尝试」付费；为未交付收钱必然引发投诉与流失，长期损失远大于单张成本；
- 我们的差异化是稳定性与诚实（今晚已经为此改掉三处「谎报已开始」的入口），这条口径与之一致。

**3. 不交付也**不等于**让用户的输入白费。**
这是今晚真正修掉的那类问题：任务失败后节点会给「重试 / 放弃」，重试从**任务记录里取回那次提交的原文**，
并且加载时发现提示词丢了会自动回填 —— **用户写过的提示词不会白写**（`a6a7e59`）。

## 三、落地动作（按优先级）

### ✅ P0 ①服务端把结果落资产 —— **已验证成立，与浏览器无关**

**证据**：今晚的照片墙 24 张、hero 3 张，全部由**无浏览器的脚本**提交（`POST /api/generation-tasks`），
跑完后我用 `GET /api/asset-items?scope=mine` 能逐一取到它们并映射成资产 id ——
说明**资产是服务端在任务终态时写的，不依赖任何客户端会话**。这正是用户观察到「退出窗口结果还在」的机制。

**结论**：这条不用改，但**要守住**：以后任何生成入口都不得把「落资产」放到前端做。

### ~~P0 ②超时基线从 300s 收紧~~ —— **本人基于实测数据撤销这条建议**

**先撤销**：我一开始写了「收紧到 120–180s」，随后用今晚自己的实测数据否掉了它：
图生图单张**实测跑到过约 17 分钟**（不是异常，是上游真实速度），若把上游超时压到 180s，
会把**本来能成功**的结果主动掐死 —— 那既伤害体验，又**白烧掉已经消耗的额度**，
反而放大了「未交付成本」这个我们正想解决的问题。

**结论**：上游超时保持 **300s** 不收紧；「别让用户干等」这件事由**客户端**解决，且已经做了：
显示已等待时长（逐秒走）、超 90 秒给「可能在上游排队」的解释、提供**真实取消**、
以及 15 分钟客户端兜底（超时就落「可重试」的失败态，而不是无限转圈）。

**这条也说明一个更普遍的原则**：涉及成本的参数（超时、并发、重试次数）不能凭直觉调，
必须用实测分布来定 —— 否则很容易把「看起来更快的设置」变成「更贵且更容易失败」。

### P1 ③异常任务自动收口（避免「卡住的账」）
服务端的任务若因锁失效等原因中断，要有定时任务把它标成失败并**释放并发额度**，
否则会出现「占着额度但永远不出结果」——那是最贵的一种损耗（额度被占满 → 新用户提交不进来）。

### P1 ④未来接入正式计费时的硬规则
- 计费只在**交付成功**时确认（`done && images.length > 0`）；
- 失败/取消/超时 → 不扣、或先扣后退（二者取一，但必须**用户侧可见**）；
- 账本要能对账：每条上游调用 ↔ 每次交付 ↔ 每笔扣减，三者可追溯。
