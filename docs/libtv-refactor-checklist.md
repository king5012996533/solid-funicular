# LibTV 功能对齐改造清单

> 这份清单是**施工队列**，不是设计文档。每一项都能独立开工、独立验收。
>
> **证据来源**（每条结论都可追溯）：
> - `[实测]` = 我登录后在其线上画布逐项点开抓下来的原文（DOM 文案 / 面板结构）
> - `[公告]` = LibTV 官方公开更新记录 `liblib.tv/feature-updates`（v1.5 / v1.0）的原文描述
> - `[现状]` = 我们仓库里实际的代码与实测行为
>
> **依赖标注**：
> - `前端` = 纯前端可完成，不依赖后端改动，也不依赖第三方 Key
> - `后端` = 需要新的服务端执行策略（现有策略只有 `image` / `agent-chat` / `agent-workspace` / `research-report`）
> - `Key` = 需要上游 API Key（当前 `ai_provider_configs` 为空表，图片生成实测已打到火山方舟并返回 `AuthenticationError`）
>
> **当前基线**：单测 9 个文件 287 项；浏览器 e2e 4 个脚本 84 项。每次改动后这些必须保持全绿。

## 2. 第一阶段：纯前端（不依赖后端、不依赖 Key）

> 这一阶段可以立刻开工、立刻验证。**建议全部做完再动后端**，因为它们同时是后续功能的容器。

### F1. 节点折叠 `前端` ✅
- **依据**：`[实测]` 节点标题前有 `▶`，展开/收起卡片主体
- **做法**：节点 data 加 `collapsed?: boolean`；折叠时卡片只留标题 + 一行参数摘要；折叠态高度固定（如 40px）；折叠不改变连线锚点位置
- **涉及**：`useWorkflowCanvas.ts`（data 类型 + 默认值）、四个节点组件、`workflow.css`
- **验收**：单测覆盖折叠态的高度计算；浏览器实测折叠/展开后连线不断、位置不跳
- **✅ 已完成**（2026-09-21）。三个节点类型（文本/图片/视频）都接上了：
  标题图标**之前**加 `▾` 开关（与 LibTV 位置一致），折叠后卡片收到 34px、
  只留一行摘要（图片/视频显示输入状态、文本显示正文开头）。
  折叠状态存在节点 data 上（能保存、能撤销、复制节点会带走）。
  实测：卡片 224→34px、连线终点 300→181 自动重新锚定、重载后仍保持折叠。
- 实测中发现并修掉一个 CSS bug：折叠摘要超长时**被硬切、没有省略号** ——
  flex 子元素显示 `text-overflow: ellipsis` 需要先有 `min-width: 0`
  （flex 项默认 `min-width: auto` 会被内容撑开）。补上后正常显示省略号。

### F2. 参数集按节点类型分开 `前端` ✅
- **依据**：`[实测]` 图片 `16:9 · 标准画质 · 2K · 1张`；视频 `16:9 · 720P · 5s · 1个`；剪辑 `16:9 · 720P · 30s`（**没有"个数"**）
- **做法**：`model-params.ts` 里的 schema 增加「节点类型维度」——同一个模型在图片节点暴露尺寸/画质/张数，在视频节点暴露比例/分辨率/时长/个数；视频补上「数量」控件（受 `capabilityJson.maxCount` 约束，默认 1 时不显示）
- **涉及**：`config/model-params.ts`、`toolbars/VideoToolbar.vue`、`scripts/seed-model-catalog.mjs`（给视频模型声明 maxCount）
- **验收**：单测断言三类节点的参数维度集合不同；浏览器实测视频节点出现「数量」步进器

### F3. composer 快捷 chip 行 `前端` ✅
- **依据**：`[实测]` 图片节点 composer 上方有 `+参考 / 标记 / 风格`；视频节点是 `参考 / 标记 / 特效 / 角色库 / 运镜`
- **做法**：在 `ContentGenerator` 里加一行可配置的能力 chip（由节点类型决定显示哪些）。**每一项必须有真实行为**，没有实现的不摆（参考 `ImageNode` 里 9 个「接入中」的教训）
  - `参考` → 就是现在的 @ 素材引用入口（已有）
  - `风格` → 预置风格提示词模板（前端可做：往提示词里插模板文本）
  - `标记` / `特效` / `角色库` / `运镜` → **先不做**，等后端能力到位
- **涉及**：`ContentGenerator.vue`、新增 chip 配置表
- **验收**：浏览器实测 chip 行渲染、点击有实际效果（不是 toast）
- **✅ 已完成**（2026-09-21）。实际只摆了 2 个：`参考`（打开 @ 素材面板）
  与 `风格`（6 个风格片段，点一次追加、再点移除，chip 显示已用数量角标）。
  `标记 / 特效 / 角色库 / 运镜` 需要后端能力，按"宁缺勿假"没有摆。

### F4. 节点开关 `前端` ✅
- **依据**：`[实测]` 视频节点底部有 `高级设置 / 联网搜索 / 自动校验素材 / 智能引用 AutoLink`
- **做法**：`ContentGenerator` 底部加开关区，按类型显示：
  - `高级设置` → 已有（`AdvancedParamsPopover`）
  - `自动校验素材` → **前端可做**：提交前校验参考图格式/可访问性，不可用就拦下并提示
  - `联网搜索` / `智能引用 AutoLink` → 需要后端能力，**先不摆**
- **涉及**：`ContentGenerator.vue`
- **验收**：提交非法参考图时被拦下且有明确提示
- **✅ 已完成**（2026-09-21）。实现过程中踩到一个**会伤害用户的 bug**，
  被 e2e 抓出来：最初的可访问性探测先发 HEAD、只在 405/501 时回落 GET，
  而这个项目的静态文件处理器**对 HEAD 返回 404**（GET 是 200）——
  结果是每一张正常的上传图都被判成"取不到"，把正常提交全拦死。
  改用 `new Image()` 探测后解决，顺带带来三个好处：判据与界面一致、
  不依赖服务端支持 HEAD、不需要 CORS（否则会出现"界面能显示、校验说不行"）。
- 顺带收口了一处重复：同样的栅格格式过滤在 `nodes/ImageNode.vue` 与
  `canana/RightPanel.vue` 里各写了一遍且行为不一致（后者漏了 `data:image/svg`），
  现在统一到 `config/reference-validation.ts`。

### F5. 节点能力预设与「下一跳」分离 `前端` ✅
- **依据**：`[实测]` LibTV 节点内的「尝试：」是**本节点的操作模式**（智能剪辑给 4 种剪辑场景）；"下一跳"是 ⊕ 手柄 + 全局添加节点面板，两件事不混
- **现状问题**：我们图片节点的「尝试」里混了 `图生视频` / `首帧图生视频` —— 那是**创建下游节点**，不是本节点能力
- **做法**：把「尝试」拆成两组，或把"创建下游"移回 ⊕ 手柄；保证每一组语义单一
- **涉及**：`ImageNode.vue` / `VideoNode.vue`
- **验收**：浏览器实测两组入口各自可达、行为符合语义
- **✅ 已完成**（2026-09-21）。实际动手时发现比我原先写的更严重：
  图片节点的 4 项里**没有一项是本节点能力** —— 图生图/图生视频/首帧图生视频
  都是"创建下游节点"（而 ⊕ 手柄那条路径已经覆盖了），「图片换背景」只弹
  「接入中」。视频节点的 2 项（全能参考/首尾帧生视频）也全是假的。
  最终做法：图片节点**不再摆「尝试」**（它目前没有可供选择的模式 ——
  图生图/文生图由有没有参考图自动决定），只留标注清楚的「生成下游节点：」
  三项；视频节点把假项换成模型声明的**真实生成方式**（点击写 `feature` 到节点
  data，经 `initialParams` 同步给工具栏），并给当前生效项加高亮。

### F6. 资产管理作为画布节点 `前端` ✅
- **依据**：`[实测]` `添加节点` 面板有「素材库 ▸ 风格库 / 特效库」；底部工具条有「资产管理」
- **做法**：新增 `asset` 节点类型，渲染资产库（复用现有资产页组件），可作为参考图来源接进下游
- **涉及**：`WorkflowNodeType`、`node-suggestions.ts`（候选规则）、新节点组件
- **验收**：单测覆盖新类型的候选规则；浏览器实测能建、能连、能当参考图
- **✅ 已完成**（2026-09-21）。新增 `asset` 节点类型 + `AssetNode.vue`：
  从素材库选一个素材、或上传本地图，选中后写 `url` 到节点 data，
  下游按图片（或视频）素材消费 —— 也就是「这张参考图从哪来」在画布上可见了。
- 配套改动：`WorkflowNodeType` 加 `asset`、`NODE_INPUT_SPECS.asset`、
  `readUpstreamKind` 认素材节点、`COHERENT_DOWNSTREAM.asset = ['image','video']`、
  画布注册、尺寸约束。加完之后**三处枚举类测试同时失败**（断言"恰好四类节点"），
  这正是它们该做的事 —— 逼着改动者显式更新契约。已更新为五类。
- 实测：双击空白 → 建出素材节点（自动带上 F1 的折叠开关）；
  空态两个入口；素材库面板能打开。当前 `asset_items` 表是空的，
  所以面板显示「素材库还是空的」—— 这是真实状态，不是加载失败。

### F7. 画布快捷键与工具条补齐 `前端` ✅
- **依据**：`[实测]` 底部工具条：`添加节点 / 移动 / 素材库 / 角色造型室 / 生成历史 / 快捷键 / 教程`；左下：`资产管理 / 整理画布(Opt+Shift+F) / 切换小地图 / 隐藏节点连线 / 网格吸附 / 缩放`
- **做法**：对齐我们已有的对应项（整理画布 = auto-layout？我们是手动；隐藏连线、网格吸附我们已有），补「快捷键」面板与「教程」入口
- **涉及**：`index.vue`、`workflow.css`
- **验收**：浏览器实测每个按钮都有行为
- **✅ 已完成**（2026-09-21）。按「宁缺勿假」只补了有真实行为的三项：
  1. **整理画布**（新增 `config/canvas-layout.ts`，纯函数 + 25 项单测）。
     用**分层布局**而不是网格：按「离根的层数」分列（取**最长**路径，
     这样多上游的节点一定落在所有上游右边，不会出现连线往左指）；
     列内按节点**当前**纵坐标排序 —— 保留用户手动调整过的相对顺序，
     整理只解决"乱"、不该重排意图。快捷键 `⌥⇧F` 与 LibTV 同一个组合键。
  2. **快捷键面板**：列的是我们**实际注册**的快捷键（Esc / ⌘Z / ⌘⇧Z / ⌘N /
     ⌘A / ⌘C / ⌘V / Delete / Space 平移，加上自己的双击建节点、⊕ 拖线），
     分画布 / 节点 / 编辑三组。不是抄 LibTV 的清单。
  3. **素材库**入口：直接建一个素材节点（复用刚做的 F6）。
- **没做「教程」** —— 我们没有教程内容，摆一个点开是空白的入口不如不摆。
- 实测：整理画布把拖乱的画布重排成左右两列且流向正确
  （拖乱后 `[[228,178],[580,370]]` → 整理后 `[[120,280],[750,220]]`）；
  快捷键面板 3 组 13 行；工具条 10 个按钮全部有行为。
- 写测试时抓到我**自己的一个错误期望**：纯环（A→B→C→A）我原以为会降级成单列，
  实际代码把它线性化成三列 —— 后者明显更好（单列会把节点叠在一起、反而看不出结构）。
  已改正期望并把这个判断写进注释。

### F8. @ 引用升级为内联 chip `前端` ✅
- **依据**：`[实测]` LibTV 的 @ 是内联 chip（带缩略图），不是纯文本
- **现状**：我们已完成 token + 解析层（`reference-resolver.ts`），**数据模型可直接复用**
- **做法**：把 `<textarea>` 换成 `contenteditable`，token 渲染成 chip；**必须处理中文 IME**（`compositionstart/end`）
- **涉及**：`ContentGenerator.vue`、`MentionPicker.vue`
- **风险**：这是本清单里前端风险最高的一项（输入法、粘贴、Enter 发送、光标位置、placeholder 全部要重做）
- **验收**：浏览器实测中文输入法组字不打断、chip 可增删、提交载荷与现在一致
- **✅ 已完成**（2026-09-21）。新增 `InlineMentionInput.vue`：受控的 contenteditable，
  **纯文本仍是唯一真相**，DOM 只是它的投影 —— 输入时把 DOM 序列化回 `@图片1`
  emit 出去，所以 `resolve-reference` 那层一行没动。已插 token 渲染成
  `contenteditable=false` 的 chip。仅在画布节点那两类 composer 启用；
  其余 13 个调用方仍是原生 textarea，行为不变。
- **IME 的三条硬约束**：① composition 期间不读也不写 DOM；
  ② `compositionend` 后补一次序列化（部分输入法最后那次 `input` 仍带 isComposing）；
  ③ 重渲染后按**纯文本偏移**还原光标（chip 是原子节点，按 DOM 偏移会偏一位）。
- **IME 验证到什么程度**：用 CDP `Input.imeSetComposition` 走浏览器真实合成管线
  （不是合成 JS 事件），确认组字期间 chip 未被重建、上屏后文本正确、
  组字中的 Enter 被当成上屏。**没验证**：真实输入法的候选窗/翻页/选词路径、
  Safari 与 Firefox 的 IME、组字起点紧贴 chip 的边界 —— headless + CDP 不是真正的输入法。
- **用户可察觉的行为差异**（相对旧 textarea）：chip 是整体、Backspace 一次删掉整个引用；
  手敲的 token 要等一个分隔符才收成 chip（为了 `@图片1` 能续着敲成 `@图片12`）；
  粘贴一律按纯文本；Cmd+Z 走浏览器原生 contenteditable 撤销栈，粒度比 textarea 粗；
  输入框自动增高（96 → 上限 40vh）。
- 顺带修了一处**只有跑起来才发现**的问题：chip 是 `document.createElement` 建的，
  拿不到 Vue 给模板节点附加的 scope 属性，所以 chip 的样式必须写成非 scoped，
  否则 chip 完全没有样式（实测当时是白字透明底）。

### F9. 画布性能压测 `前端` ✅
- **依据**：`[公告]` v1.5「优化大量节点的画布（数千节点）卡顿体验问题」「修复画布偶尔丢失节点的问题」
- **做法**：造 1000 / 3000 节点画布，测拖拽帧率与首屏时间；若卡，按需加虚拟化
- **涉及**：`index.vue` / `useWorkflowCanvas.ts`
- **验收**：给出实测数字（帧率 / 时间），不接受"感觉还行"
- **✅ 已完成**（2026-09-21）。新增可复现的压测脚本 `tests/e2e/canvas-perf.mjs`
  （直接造夹具写库 → 加载 → 量首屏与拖拽帧率 → 自动清理）。

**实测数字**（1600×1000 视口，真实鼠标拖拽 60 步）：

| 节点数 | 视口虚拟化 | 渲染稳定 | 拖拽帧率 |
|---|---|---|---|
| 100 | 关 | 1693 ms | **58.9 FPS** |
| 300 | 关 | 3119 ms | **60.6 FPS** |
| 300 | 开 | 1585 ms | 37.7 FPS |
| 1000 | 关 | 8302 ms | 24.1 FPS |
| 1000 | 开 | 3079 ms | 15.2 FPS |

**结论（与直觉相反，以数据为准）**
1. **300 节点以内是满帧的**，不用优化。
2. **视口虚拟化（`onlyRenderVisibleElements`）持续伤害拖拽帧率**
   （300 节点 60.6 → 37.7），只换来加载时间减半。原因是拖拽时每帧都要重算
   可见集合并频繁增删 DOM，比"保留全部节点、只移动一个"更贵。
   **所以没有启用它** —— 这个产品的主交互就是拖节点。
3. 1000 节点两种配置都不合格（24 / 15 FPS），真正的原因是**节点组件太重**
   （每个都渲染工具条、图标、子菜单），不是图遍历。

**已经做的优化**：把「每个节点/边各自遍历整个 edges/nodes」改成共享索引
（`composables/workflow-graph-index.ts`）。原先 1000 节点下是 O(N×E) ——
950 条边组件 × 每条扫 950 条 ≈ 每帧 90 万次操作。索引化后每帧只重建一次。
**诚实地说：这个改动只把首屏从 2319ms 降到 1859ms，帧率基本没动**
（24.3 → 24.1）。最初我根据"去掉边会快 5.6 倍"的对照组推断瓶颈在边遍历，
那是错的 —— 快是因为少渲染 950 个 SVG 边组件，不是因为少遍历。

详见 **F9b**。

### F9b. 画布性能根治：拿掉每帧快照与每帧警告 `前端` ✅
- **✅ 已完成**（2026-09-21）。**这一项我前后猜错三次，最后靠 profiler 才找对**，
  所以把过程一并记下来 —— 免得以后又从"看起来最可疑的地方"下手。
- **三次错误假设**：
  1. F9 时按「去掉边会快 5.6 倍」推断瓶颈在**边遍历** → 索引化后帧率没变（错）
  2. F9b 时推断是**节点卡片内容太重** → 把全部节点折叠（卡片内容几乎不渲染）
     后帧率**一点没变**（错）
  3. 看到 profile 里 `warn$1` 占 22% 时，怀疑是 `selectionKeyCode` 的 prop
     校验警告 → A/B 把它换成合法值后热点纹丝不动（错）
- **改用 profiler 找到的两个真凶**（新增 `tests/e2e/profile-drag.mjs`：
  用 CDP 抓 V8 CPU profile，按函数聚合自耗时排行）：

  **① 每帧 `JSON.stringify` 整张画布（占拖拽 CPU 的 50.9%）**
  `currentCanvasSnapshot` 是个 computed，用来判断「相对上次保存有没有变化」，
  而它 `JSON.stringify(nodes.value)` 会读遍每个节点的每个属性 —— 于是拖拽时
  position 每帧变化都会让它失效、下一帧整张画布重新序列化 + 多 MB 字符串比对。
  改成**防抖结算**（400ms）：判断"要不要保存"不需要帧级精度，用户看不出这 400ms。

  **② 每帧一次的 Vue 警告（占 22%）**
  绕开控制台去重、直接计数后发现：拖拽 2 秒内触发 **977 次**
  `[Vue warn]: Extraneous non-props attributes (sourceNode, targetNode, type, updatable …)`。
  原因是自定义边组件没声明 Vue Flow 传进来的那些内部属性，Vue 就把它们当外部属性
  处理、每次渲染都警告 —— 而 `warn` 内部会调 `getComponentTrace()` 遍历组件栈。
  在四个边组件上加 `inheritAttrs: false`（明确「不转发未知属性」）。
  **DOM 本身一直是干净的**，纯粹是警告的开销。

- **实测效果**（1000 节点，真实鼠标拖拽 60 步）：

  | 指标 | 原始 | 修①后 | 修②后 |
  |---|---|---|---|
  | 拖拽帧率 | 24.2 FPS | 42.9 | **53.7 FPS** |
  | 渲染稳定 | 8541 ms | 3799 | **2151 ms** |
  | CPU 采样数 | 20073 | 7592 | **5511** |
  | `warn$1` 热点 | — | 22.6% | **消失** |

  300 节点 60.4 FPS（基线 60.6，在噪声内，不算退化）。
- **行为变更已单独验证**：快照防抖会影响 autosave 触发时机，实测
  「加两个节点 → 等防抖 → 库里节点数与 DOM 一致」（2 → 4，DOM 4）。
- **顺带修好测试基建的一处误判**：巡检类脚本的「无 console error」断言会因为
  **第三方热链资源**解析失败而误报（代理一开，首页 32 张 `qwe-oss` 的图全裂成
  `ERR_NAME_NOT_RESOLVED`）。抽出 `tests/e2e/lib/console-filters.mjs`，
  把「我们自己的报错」与「第三方资源失败」分开：前者判失败，后者只统计并报出来。
  **不隐藏** —— 它本身就是下面 §5 记的真实风险。

### K1. 图片生成真正跑通 `Key` ✅
- **依据**：`[实测]` 我已把链路打到火山方舟并拿到 `AuthenticationError: API key missing or invalid`；`generation_records` 因此只有 1 条失败记录

- **验收**：真出一张图并落进 `generation_records`（`status=SUCCESS`）
- **✅ 已完成**（2026-09-21）。配了 ggwk1 中转站（`https://www.ggwk1.online/v1`，
  OpenAI 兼容，11 个图像/视频模型），密钥走后台自己的接口写入（由后端加密）。
  新建模型 `GPT Image 2`（`gpt-image-2`），能力按**实测**填写：
  返回 base64（应用侧本来就支持，见 `upstream-shared-parser` 的 b64_json 分支）、
  单张 50~228 秒、n>1 在 5 分钟内没完成所以 `maxImagesPerRequest: 1`。

- **打通过程中发现并修掉一个影响面很大的 bug**（不是本次改动引入的，是一直存在）：
  `server/redis/config.ts` 的 `normalizeInteger()` 用 `Number(value)` 判非法，
  而调用方一律传 `process.env.X || ''` —— **`Number('')` 等于 0 而不是 NaN**，
  于是"未设置"被当成"显式配了 0"，最后 `Math.max(minValue, 0)` 返回 **1**。
  结果是**所有没在 .env 里配置的 Redis 参数全变成 1**，其中
  `taskLockTtlMs = 1 毫秒` 让任务执行锁瞬间过期、续期必然 `ownership_lost`
  → **任何耗时超过 5 秒的生成任务都会被中断**。
  这正是「这个库里从来没成功出过图」的直接原因：之前 seedream 的失败是上游秒回的
  认证错误（没活到 5 秒），真正开始生成的任务活不过 5 秒。
  修法：先判空字符串再判数值，并补了 15 项单测钉住（含"锁 TTL 不能是 1 毫秒"这条回归）。

- **上游超时也按实测放宽**：原来是 `90s + (n-1)×60s`（注释按直连官方 API 估的
  "单张 5-30s"）。实测这个中转站同一档参数耗时 50 / 82 / 195 / 228 秒，差 4 倍。
  基线改为 300s、每张 90s、上限 600s。它只是上限不是延迟。

## 5. 明确不做 / 存疑

| 项 | 结论 | 理由 |
|---|---|---|
| 站外链接的字节 CDN 素材 | **待清**（方案 A 已定：只修坏的） | 热链不算再分发，不是法律急事；但 `homeDiscoverContent.json` 41 处指向个人 OSS bucket，有失效风险 |
| 9 个「接入中」占位按钮（全景图 / HD 增强 / 编辑元素 / 角度 / 打光 / 裁剪） | **已接线**（除「编辑元素」） | 实测这些大多是"固定指令 + 图生图"，不需要新后端：裁剪纯前端，角度/打光/HD 增强/全景图 走已验证的 image-edit 管线。**编辑元素（局部重绘）做不了** —— 见下一行 |
| 「编辑元素」局部重绘（涂抹蒙版） | **待定**（不是"不支持"，见下） | 2026-09-21 实测记录，**先纠正一个误判**：第一次带 `mask` 的请求 13 秒返回 400，我据此判断"上游不收这个参数"——错了。**重试同一个带 mask 的请求返回 200、334 秒出图**；同图同提示词不带 mask 的对照是 200、265 秒。所以那句 400 是中转站的偶发失败（不带 mask 的请求也出现过同样一句），**不能作为"不支持蒙版"的证据**。目前只能确认「参数被接受」，**还没验证蒙版是否真的生效**（透明区外是否原样保留）—— 要验证只需再发一次带 mask 的请求、把 b64 存下来，对比圆外区域与输入图是否一致。**复用配方**（确认可用后照做）：`src/shared/upstream-request-normalizer.ts` 的 `buildImageEditRequestFormData` 增加 `mask` 入参并 `formData.append('mask', blob, 'mask.png')`（务必校验 `blob.type === 'image/png'`，jpg 没有 alpha）；`RequestImageEditInput` 与 `image-task-executor` 各透传一层；再配一个涂抹蒙版 UI。各层都很浅 |
| 无后端支撑的纯展示项 | **不做** | 宁缺勿假：摆一个点了没反应的入口，比不摆更差 |
| 重复的 `canvas.css` 导入 | 低优先 | `workflow.css` 与 `canvas-shell/index.css` 都引了 `canvas.css`，重复但无害 |
